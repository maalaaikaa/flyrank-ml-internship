<section>
    <h2>Abstract</h2>

    <p>
        This project asks which content items should be prioritized for
        human review when a content team has more pages than it can
        refresh at once. I use FlyRank search intelligence data to build
        a repeatable ranking workflow based on observed search, click,
        position, and engagement signals. The workflow first establishes
        a transparent baseline action score and then compares it with a
        Random Forest regression model for <code>trend_pct</code>, using
        a client-grouped holdout split and explicit leakage checks.
        The model and baseline are evaluated on the same held-out content,
        with the results generated directly from the dataset.
        The final output is a ranked review queue with reason codes
        intended as decision-support rather than proof of causality or
        guaranteed refresh impact.
    </p>
</section>


<section>
    <h2>1. Introduction / Problem Statement</h2>

    <p>
        Content teams often have more pages available for review than
        they can reasonably inspect or refresh at one time. This creates
        a prioritization problem: which content should be examined first?
    </p>

    <p>
        The purpose of this project is to create a repeatable,
        evidence-based way to prioritize content review using available
        Search Intelligence signals.
    </p>

    <p>
        The project belongs to the
        <strong>Refresh / Content Opportunity Scoring</strong> lane.
    </p>

    <div class="highlight">
        <strong>Decision supported:</strong>
        The system recommends which content items deserve human review
        first. It does not automatically recommend that a page must be
        refreshed.
    </div>
</section>


<section>
    <h2>2. Data</h2>

    <p>
        The analysis uses the FlyRank ML Internship Search Intelligence
        dataset. The working data contains content-level measurements
        describing search demand, competition, content characteristics,
        visibility, click-through behavior, engagement, and observed
        trend movement.
    </p>

    <h3>Unit of analysis</h3>

    <p>
        One row represents one content item identified by
        <code>content_id</code>.
    </p>

    <h3>Target</h3>

    <p>
        The modeling target is <code>trend_pct</code>, a continuous
        observed trend measure available in the dataset.
    </p>

    <h3>Excluded fields</h3>

    <ul>
        <li><code>content_id</code> — identifier only.</li>
        <li><code>client_id</code> — used for grouped validation, not prediction.</li>
        <li><code>trend_pct</code> — the modeling target.</li>
        <li><code>trend_direction</code> — target-derived and therefore a leakage risk.</li>
        <li>Tier/bucket fields — excluded where they duplicate underlying numeric measurements.</li>
    </ul>

    <p>
        No client names, domains, private queries, credentials, or raw
        private exports are included in this public research presentation.
    </p>
</section>


<section>
    <h2>3. Methodology</h2>

    <h3>Baseline</h3>

    <p>
        A transparent baseline action score combines four observed
        signals:
    </p>

    <ul>
        <li>Low CTR — 30%</li>
        <li>Poor average position — 30%</li>
        <li>Low engagement — 25%</li>
        <li>High search demand — 15%</li>
    </ul>

    <p>
        A higher score means that the content item receives higher
        priority for human review.
    </p>

    <h3>Machine-learning model</h3>

    <p>
        A Random Forest Regressor is used to model the continuous
        <code>trend_pct</code> target. Numeric features are median
        imputed, while categorical features are imputed and
        one-hot encoded.
    </p>

    <h3>Validation</h3>

    <p>
        The dataset is divided using an 80/20 client-grouped holdout.
        This prevents the same client from appearing in both training
        and testing data.
    </p>

    <p>
        The baseline and machine-learning model are evaluated on the
        same held-out test set.
    </p>

    <h3>Leakage control</h3>

    <p>
        Target-derived fields, identifiers, and excluded bucket fields
        are not used as predictive features. This helps prevent the model
        from learning information that would not be appropriate as an
        input signal.
    </p>
</section>

<section>
    <h2>5. Limitations & Honest Framing</h2>

    <p>
        This analysis uses observational data. It can identify
        associations and directional patterns but cannot establish that
        changing a page will cause a particular change in search
        performance.
    </p>

    <p>
        The model is also limited by the variables available in the
        dataset. Editorial quality, competitive changes, seasonality,
        business context, and other external factors may not be fully
        represented.
    </p>

    <p>
        Client-grouped validation reduces client leakage but does not
        transform the analysis into a causal experiment.
    </p>

    <p>
        The final recommendation should therefore be interpreted as a
        <strong>human-review priority</strong>, not an automatic refresh
        instruction or guarantee of future performance.
    </p>

    <div class="highlight">
        <strong>Framing:</strong>
        observed · measured · directional · decision-support
    </div>
</section>


<section>
    <h2>6. Ranked Recommendations</h2>

    <p>
        The final output is a ranked content-review queue. Each item is
        assigned an action score and reason code so that the priority
        is interpretable.
    </p>

    <h3>Recommendation logic</h3>

    <ul>
        <li><strong>LOW_CTR:</strong> observed low click-through signal.</li>
        <li><strong>POOR_POSITION:</strong> observed weaker search position.</li>
        <li><strong>LOW_ENGAGEMENT:</strong> observed lower engagement.</li>
        <li><strong>HIGH_DEMAND:</strong> observed higher search demand.</li>
        <li><strong>MULTI_SIGNAL:</strong> multiple signals contribute to the priority.</li>
    </ul>

    <div class="highlight">
        The Top-20 recommendation table should be inserted from
        <code>capstone_ranked_recommendations.csv</code> generated by
        the notebook.
    </div>
</section>

<section>
    <h2>8. Reproducibility</h2>

    <p>
        The project is organized as a sequence of weekly notebooks
        covering the data contract, leakage checks, signal audit,
        baseline scoring, model training, and final capstone analysis.
    </p>

    <ol>
        <li>Define the unit of analysis and target.</li>
        <li>Identify excluded and leakage-prone fields.</li>
        <li>Audit candidate signals.</li>
        <li>Build the transparent baseline.</li>
        <li>Split data by client.</li>
        <li>Train the Random Forest model.</li>
        <li>Evaluate model and baseline on the same test set.</li>
        <li>Generate the ranked recommendation queue.</li>
    </ol>

    <p>
        The corresponding notebooks and generated outputs are maintained
        in the project repository.
