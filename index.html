Abstract

This project asks which content items should be prioritized for human review when a content team has more pages than it can refresh at once. I use FlyRank search intelligence data to build a repeatable ranking workflow based on observed search, click, position, and engagement signals. The workflow first establishes a transparent baseline action score and then compares it with a Random Forest regression model for trend_pct, using a client-grouped holdout split and explicit leakage checks. The model and baseline are evaluated on the same held-out content using regression error and ranking alignment. The final output is a ranked review queue with reason codes intended as decision-support rather than proof of causality or guaranteed refresh impact.

1. Introduction / Problem Statement

Content teams often have more pages available for review than they can reasonably inspect or refresh at one time. This creates a prioritization problem: which content should be examined first?

This project creates a repeatable, evidence-based approach for prioritizing content review using available Search Intelligence signals.

Decision supported: The system identifies content items that deserve human review first. It does not automatically decide that a page must be refreshed.

2. Data

The analysis uses the FlyRank ML Internship Search Intelligence dataset. The working data contains content-level measurements describing search demand, competition, content characteristics, visibility, click-through behavior, engagement, and observed trend movement.

Unit of analysis

One row represents one content item identified by content_id.

Target

The modeling target is trend_pct, a continuous observed trend measure available in the dataset.

View excluded fields
  • content_id — identifier only.
  • client_id — used for grouped validation, not prediction.
  • trend_pct — modeling target.
  • trend_direction — target-derived and therefore a leakage risk.
  • Tier/bucket fields — excluded where they duplicate underlying numeric measurements.
Public-safety rule: No client names, private queries, credentials, domains, private URLs, or raw private exports are included.

3. Methodology

Baseline action score

The transparent baseline combines four observed signals:

  • Low CTR — 30%
  • Poor average position — 30%
  • Low engagement — 25%
  • High search demand — 15%

A higher score means higher priority for human review.

Random Forest model

A Random Forest Regressor is used to model the continuous trend_pct target.

Numeric features are median-imputed. Categorical features are imputed and one-hot encoded.

Validation design

The data uses an 80/20 client-grouped holdout split. The same client cannot appear in both training and test groups.

Leakage controls

Target-derived fields, identifiers, and excluded tier fields are not used as predictive features.

5. Limitations & Honest Framing

Observational data

The dataset is observational. The analysis can identify associations and directional patterns but cannot establish that changing a page causes a particular change in search performance.

Missing business context

Editorial quality, competitive changes, seasonality, business priorities, and other external factors may not be represented.

Validation limitation

Client-grouped validation reduces client leakage but does not make this a causal experiment.

Honest framing: observed · measured · directional · decision-support

7. Artifacts

The analysis produces several artifacts designed to make the workflow inspectable and useful to a content team.

  • Model-versus-baseline comparison
  • Priority ranking comparison
  • Top-20 recommendation queue
  • Random Forest feature importance
  • Largest prediction-error analysis
Why these artifacts?

The goal is not to create a large collection of charts. Each artifact should answer a practical question: how well does the approach perform, why were items prioritized, and where does the model appear uncertain or wrong?

8. Reproducibility

The project is organized as a sequence of weekly notebooks covering data-contract design, leakage checks, signal audit, baseline scoring, model training, and final capstone analysis.

  1. Define the unit of analysis and target.
  2. Identify excluded and leakage-prone fields.
  3. Audit candidate signals.
  4. Build the transparent baseline.
  5. Split data by client.
  6. Train the Random Forest model.
  7. Evaluate model and baseline on the same test set.
  8. Generate the ranked recommendation queue.
