Abstract

This project investigates which content pages should be prioritized for human review and potential refresh when content teams have more pages than they can inspect at once. The analysis uses FlyRank Search Intelligence data and observed search, visibility, click-through, engagement, and trend signals to create a repeatable prioritization workflow. A transparent baseline action score is constructed first and then compared with a machine learning model using the same grouped validation design. Potential leakage is addressed by excluding identifiers and target-derived variables from the predictive feature set. The final output is a ranked content refresh queue with reason codes designed for decision-support rather than proof of causality or guaranteed refresh impact.

1. Introduction / Problem Statement

Content teams often manage hundreds or thousands of pages and cannot review or refresh every page at the same time. The main challenge is deciding which pages should receive attention first.

This project develops a repeatable prioritization workflow using observed search, visibility, engagement, and trend signals. The goal is to rank content pages according to their priority for human review and possible content refresh.

Decision supported: The output helps a content team decide which pages should be investigated first for a potential content refresh. The ranking supports human decision-making and does not guarantee that refreshing a page will improve its search performance.

2. Data

This project uses the FlyRank ML Internship Search Intelligence dataset. The data contains content-level observations with search demand, competition, content characteristics, click-through rate, average position, engagement, scrolling behavior, and observed trend signals.

Unit of Analysis

One row represents one content item identified by a content-level identifier.

Modeling Target

The modeling workflow uses the target defined in the project notebook. In the current implementation, the observed trend_pct field is used as the continuous target for the machine learning comparison.

Fields excluded from prediction
  • content_id — excluded because it is an identifier and does not represent a generalizable content signal.
  • client_id — excluded from prediction and used for grouped validation to reduce overly optimistic evaluation caused by client-level similarity.
  • trend_pct — excluded from features because it is the prediction target.
  • trend_direction — excluded because it is directly related to the target and could create leakage.
  • Identifier-like, target-derived, or redundant derived fields are excluded when they could introduce leakage or duplicate information already represented by the original measurement.
Public-safe data rule: This research paper does not display client names, domains, private URLs, private search queries, credentials, or raw private data exports.

3. Methodology

Feature Engineering

Numeric variables are handled using appropriate missing-value treatment, including median imputation where required. Categorical variables are handled through missing-value treatment and encoding. Identifier fields and target-derived fields are excluded from the predictive feature vector.

Baseline Action Score

A transparent baseline action score combines safe observed signals such as search demand, click-through rate, average position, engagement, scrolling behavior, and trend information according to the rules defined in the project notebook. The baseline produces an interpretable ranking and reason codes for human review.

Machine Learning Model

A Random Forest regression model is used to learn potentially non-linear relationships between the available search and content features and the observed continuous target. The model is compared against the baseline using the same validation logic.

Validation Design

The train and test data are separated using grouped validation based on client-level grouping. This reduces the possibility that highly similar observations from the same client appear in both the training and evaluation data.

Leakage Checks

Identifier columns, the target itself, and variables derived directly from the target are excluded. Features are also reviewed to determine whether they are available before the intended prediction or prioritization moment.

4. Results

The baseline scoring approach and machine learning model are evaluated using the same validation design. Results should be interpreted as observed performance on held-out data rather than evidence that refreshing content causes a specific outcome.

5. Limitations & Honest Framing

Observational Data

This analysis uses observational data. It can identify measured patterns and associations but cannot prove that a content refresh causes a particular performance outcome.

Missing Context

Factors such as editorial quality, seasonality, competitor activity, search algorithm changes, and business priorities may not be fully represented in the available dataset.

Model Limitations

Model performance depends on the available data, feature definitions, target definition, and validation design. Performance may differ when applied to future or different data.

Honest framing: Observed · Measured · Directional · Decision-Support

7. Reproducibility

The project is structured as a sequence of notebooks covering data contracts, feature engineering, leakage checks, signal auditing, baseline scoring, machine learning, validation, and ranked content refresh recommendations.

  1. Define the research question and unit of analysis.
  2. Classify fields as features, labels, context, or excluded.
  3. Check data quality and missing values.
  4. Audit safe search and content signals.
  5. Build a transparent baseline action score.
  6. Perform grouped validation.
  7. Train and evaluate the machine learning model.
  8. Generate ranked content refresh recommendations with reason codes.
Reproducibility: The notebooks used for this analysis are stored in the project repository under the required project structure.
